## 1. 三段式项目介绍

### 30 秒版（自我介绍里的项目带过）

> 我独立开发了一个面向农户的病虫害智能诊断系统：拍照或描述症状，系统走一条 9 节点的
> Agent 流水线——意图识别、多模态识别、RAG 检索、置信度闸门、用药规则校验，最后流式
> 输出带引用的回答。技术上最有特点的三点：自研 Agent 框架同时支持固定管线和
> Function calling 工具循环两种形态；置信度是三个可计算分量的加权而不是模型自报；
> 全程评测驱动——检索命中率、82 项端到端冒烟、53 项单测守着每次改动。

### 2 分钟版（面试官说"详细讲讲"时）

按「业务问题 → 架构 → 三个技术亮点 → 量化结果」讲：

1. **业务问题**：农户拍张病叶照片，需要一个"识别 → 告诉怎么治 → 推荐登记过的药"
   的闭环。这个场景的特殊约束是**错误代价极高**（用错药）且**用户无法自我纠错**
   （农户不懂植保），所以整个系统的设计核心是"不确定就不给结论"。
2. **架构**：FastAPI 后端 + PostgreSQL/pgvector + Redis + 零依赖静态前端。
   Agent 层是自研的有限状态机：intent → context → diagnose → retrieve →
   rule_check → compose → persist → remind，外加置信度闸门（闸门 A）和用药
   规则引擎（闸门 B）两道拦截。
3. **三个技术亮点**（见第 5 节故事，挑面试官背景展开）：
   - 检索评测驱动：36 条口语化评测集，hit@3 从 81% 迭代到 97%，每一步都有归因；
   - 双模态通道：本地训练的 PlantVillage 分类器（39 类，验证集 99.89%）出可复现
     概率 + 通用 VLM 出解释，合并后进置信度；
   - 降级可见：天气/存储/LLM/分类器四条依赖各有降级路径且全部对用户可见。
4. **量化**：82 项 HTTP 冒烟、53 项单测、30 项真实浏览器 e2e、用药登记覆盖
   80/101 种病虫害。

## 3. 高频问题与参考回答

### 3.1 项目整体与选型

**Q：为什么自己写 Agent 框架，不用 LangGraph / Dify？**

考点：技术选型的判断力，有没有跟风。

> 两种形态我都有，但分场景：**诊断主链路是确定性流程**——固定 9 个节点，不需要动态
> 图编排；而我最需要的是**可观测性**：每个节点的耗时、每次工具调用的参数与结果、
> 失败在哪一步，全部落库（chat_messages.trace），出问题能精确回答"是哪一步、为什么"。
> 自研 FSM 只有几百行，换来的是节点级工具白名单（越权调用直接拒绝并留痕）和单节点可测。
> **但咨询类问题是开放性的**——回答"现在适合打药吗"可能需要天气、地块、知识库三种
> 信息的任意组合，固定管线没法预判，所以这条路径我用 OpenAI Function calling 做了
> 工具循环，让 LLM 自主决定调什么工具。所以我的答案是"按问题性质选形态"，而不是
> 全盘倒向某一种——诊断用 workflow 的确定性，咨询用 tool-loop 的灵活性。

**追问：两种形态怎么共存？** INTENT_ROUTES 里每个意图映射不同的节点序列；
工具循环只负责**收集证据**，最终回答仍走统一 compose（流式+输出护栏），两条路径
共享同一个出口纪律。

**Q：为什么 pgvector，不用 Milvus / 单独向量库？**

> 当前规模 119 个 chunk、目标准备到万级，PG 一套系统同时承载业务数据和向量，
> 事务一致性好、运维成本低，且向量检索可以和元数据过滤（作物/审核状态）在一条
> SQL 里完成——这在"检索前过滤"场景比跨系统方案简单得多。如果量级到百万 chunk
> 或需要多副本，我会迁 Milvus/Qdrant，检索层已抽象（HybridRetriever），迁移面可控。
> 另外我做了混合检索，向量只是其中一路，纯向量库反而不够。

**Q：这个项目最大的难点？**

> 不是某个算法，是"错误代价高"带来的系统性设计。农户拿系统给的药去用，说错会出事。
> 所以我做了三层防线：置信度闸门（不确定就不给结论，要求补拍）、规则引擎（只在
> 农药登记范围内推荐，剂量一律指向标签）、输出护栏（即使 LLM 生成，剂量命中拦截
> 规则的句子也会被剔除）。第三层是关键——LLM 生成的内容也要过护栏，不能信任。

### 3.2 RAG

**Q：chunk 怎么切的？参数怎么定的？**

> 三级瀑布：整篇 ≤420 字原样一块（短文不硬切）；超长先按 **Markdown 标题分节**
> （识别要点/发生条件/防治要点各自成块，查"怎么防"不会被症状长文稀释）；节内按
> 段落→句子贪心合并到 size；节标题冗余到每个 chunk（单独一块也知道自己在讲什么）。
> 420 字对应 bge-small-zh 的有效上下文甜点区，overlap 60 防答案落在切口。
> 有两个工程细节：标题前缀的长度要**先从 size 预算里扣**（否则产生超长块，自测
> 抓过这个 bug）；合并时按集合比较判断是否真的变化（用 sorted 整表比较会把顺序
> 重排误报成更新）。

**Q：检索怎么评估的？**

> 36 条**口语化**评测集：农户的真实问法（"叶背有白毛像撒了面粉"）→ 期望命中的病害，
> 判定 hit@1/hit@3。刻意用本地改写（不调 LLM）测"检索地板"，保证可复现、可进 CI。
> 用它驱动了三次迭代：别名映射（西红柿→番茄，hit@1 67→72%）、标题命中作为第三路
> RRF 信号、语料扩充后增厚机制——最终 hit@1 69% / hit@3 97%。
> 评测集进 pytest，hit@3 低于 60% 视为回归。

**Q：混合检索怎么做的？为什么用 RRF 不用加权求和？**

> 向量（pgvector 余弦）+ BM25（jieba 分词）两路召回，RRF 按排名融合：score =
> Σ w/(k+rank)。不用加权和是因为向量分和 BM25 分**量纲完全不同**，加权要调一个
> 说不清道理的系数；RRF 只用排名，k=60 与通道数解耦。后来加了第三路"标题命中"
> （标题命中查询词的个数作为独立排名，低权重并入），解决症状两路召回被同作物
> 近似病害稀释、而病名查询反而排不上的问题——仍然只用排名，不引入新量纲。
> 归一化用理论最高分 Σw/(k+1) 做分母——这是置信度 margin 分量的前提，原始 RRF
> 分差 0.0164 会把 margin 结构性压死，闸门就退化成永远拦截。

**Q：知识库数据哪来的？可信吗？**

> 分三层答：① 内容按公开植保常识由 LLM 辅助整理成结构化条目，**来源分级**
> （official/academic/community）且逐条标注"待补充文献出处"，review_status 字段
> 齐备——数据模型里审核流是完整的，只差审核动作；② 结构化发生条件
> （温湿度/降雨阈值）是唯一事实来源，天气风险打分和给农户看的正文都从它渲染，
> 杜绝两处手写漂移；③ **用药数据是独立的规则引擎校验**——只推荐登记范围内的药、
> 剂量一律指向标签原文，知识内容错了也不会导致错误用药建议。

**Q：怎么控制幻觉？**

> 三层：① 提示词层——CONSULT_SYSTEM 明确"检索结果里没有的必须说没有资料"；
> ② 结构层——compose 的输入是检索块+规则放行清单，置信度不足时**不把任何放行
> 产品交给模型**，模型想推荐也没材料；③ 输出层——护栏按拦截规则剔除剂量句。
> 另外诊断结论必须过置信度闸门，未通过就转"要求补拍"而不是硬答。

### 3.3 Agent 设计

**Q：Function calling 工具循环怎么实现的？和 workflow 的边界在哪？**

> 咨询路径的 TOOL_LOOP 节点：给 LLM 三个工具（知识库检索/天气风险/农场地块）
> 的 JSON Schema，`tool_choice=auto` 循环最多 3 轮，LLM 自主决定调什么、调几次；
> 每轮工具结果以 tool 消息回灌，**循环只收集证据**，最终回答仍由统一 compose
> 生成（流式+护栏+三段式），两条路径共享出口纪律。三个工程细节：
> ① 路由裁剪的兜底必须沿"路线"找而不能沿主链——我加新节点时被静默跳过过一次，
> 无任何报错，靠读 SSE 轨迹发现；
> ② 工具结果序列化要在协议边界处理非 JSON 类型（date 用 default=str），否则
> 异常被通用兜底吞成"跳过"；
> ③ 模型会"自信跳过"工具直接 DONE——所以代码层保证"没查过知识库就强制补一次
> 检索"，安全约束不赌模型守约。留痕：每次工具调用写 tool_calls 落库，事后可复盘
> "哪一步查了什么"。

**Q：置信度怎么算的？为什么不用模型自报置信度？**

> 模型自报的 0.9 是措辞习惯，不可校准。我的置信度是三个可计算分量的加权：
> **margin**（结论与最强竞争候选的证据分差，按 RRF 理论最高分归一化）、
> **agreement**（多张照片结论一致率；单图给中性值 0.6，不给满分——没证据不等于
> 证据强）、**coverage**（结论自身拿到的证据强度）。每个分量都能追溯到具体数据。
> 后来把本地分类器作为"第三个观察者"接进来：强确认（与结论同名、概率高、与次选
> 区分大）抬升一致性并托底证据强度；强分歧压低一致性（两通道打架更保守）；无声不变。
> 阈值 0.55，低于就转"要求补拍"——不确定就不给结论，这是这个业务的核心纪律。

**Q：闸门拦截后为什么还要落库？**

> 被拦截的恰恰是最有价值的数据：有多少比例没答上来、补拍后二次判断是否命中，
> 这是评估和改进的依据，也是 badcase 库的原料。早期有个 bug 是拦截分支直接 return
> 导致 PERSIST 节点永远不执行，两个状态成了死代码——修法是"任何终止点都先落库"。

**Q：多轮记忆怎么做的？**

> 会话消息成对落库（user/assistant，含轨迹/工具调用/引用），run 开始时读最近 8 条
> 回灌进意图识别和 compose。实测效果："那辣椒呢"单独看是病句，带历史后模型能解析出
> 作物=辣椒并转诊断路径。这里踩过一个架构坑：前端最初每次提问生成新 session_id，
> 记忆永远为空——修成"同一话题复用会话、显式开新话题"，顺带解决了会话列表碎片化。

### 3.4 多模态识别

**Q：识别怎么做的？准确率多少？**

> 双通道：本地训练的 ResNet18（PlantVillage 39 类、5.5 万张图，验证集 99.89%，
> ONNX CPU 推理 <100ms）出可复现的 top-k 概率；Qwen3-VL-32B 出解释和建议。
> 合并策略：分类器强候选（概率≥0.6 且与次选区分明显）置顶参与 top1 解析，
> 与 VLM 同名时给候选补上概率作为一致性证据。
> 诚实地说：99.89% 是**温室标准图**上的成绩，真实田间实拍存在 domain gap——
> 我实测过一张实拍图，分类器 top1 概率只有 0.0004。所以系统设计上分类器低置信
> 时静默退回 VLM 主导，绝不硬凑；根本的解决是把实拍照片积累起来继续微调。

**Q：那为什么还要训练专用分类器？VLM 不就行了吗？**

> 两个理由：① **可校准性**——VLM 说"我觉得是 XX，置信度 0.9"不可复算，分类器的
> softmax 概率是真实分布，能当闸门的证据；② **成本与延迟**——ONNX CPU 推理
> <100ms 零 API 成本，每个请求都先过它，只有需要解释时才调 VLM。而且分类器对
> 训练分布内的图是决定性的：实测训练集同分布图 prob=1.0，闸门直接放行。

**Q：VLM 的提示词怎么设计的？**

> 植保专家角色 + 安全规则（不确诊不给药名）+ 强制 JSON 输出结构
> （image_quality / candidates / per_image / missing_shots）。有个专门的接线检查
> 脚本：替换掉真正发请求的层，断言 system 提示词和 schema 确实进了消息体——
> 因为曾发生过"提示词定义了却没传给模型"的静默失效（整条视觉链路当时从未真正
> 执行过），检查器就是为这类"测试覆盖不到的分支"造的。

### 3.5 工程化与可靠性

**Q：SSE 流式怎么实现的？**

> 一次性接口和流式接口共用同一个 Agent：流式路由往 ctx 注入一个 asyncio.Queue，
> compose 节点优先走 `llm.stream()` 逐段把 delta 推进队列，路由 50ms 轮询排空后
> 以 delta 事件转发；一次性路由不注入队列，代码路径不变。两个细节：① 流出去的是
> 输出护栏**前**的原文，final 事件才是护栏后的权威版本，前端以 final 覆盖——
> "立刻看到字"与"输出合规"的折中；② 后端对前端静态资源加了
> `Cache-Control: no-cache`——零依赖前端 JS 之间有版本耦合，浏览器启发式缓存
> 曾造成新旧混合运行报错。

**Q：如果 LLM 挂了/超时怎么办？**

> 全链路分级降级：LLM 客户端带重试+备用模型配置位；意图识别降级到本地词典+规则，
> 查询改写降级到口语映射表，回答生成降级到模板；天气接口失败只关闭天气增强，
> 不影响诊断。关键是**降级必须可见**：health 端点暴露 storage 实际后端、天气响应带
> is_mock+caveat、分类器 available 状态可查——禁止"进程活着但功能全废却报正常"。
> 我甚至因此修过一个测试：把"断言落在当前环境值"改成"以 health 为真值来源"。

**Q：怎么发现这些静默失效的？**

> 方法论：**先建尺子再动刀**。82 项 HTTP 冒烟（真实登录+全链路）、36 条检索评测、
> 各组件的接线检查（替换网络层断言消息体）、50+ 项单测、30 项真实浏览器 e2e
> （DOM 桩测不到 CSS，必须真实渲染）。举两个例子：跨地块天气聚合把 3 天降雨算成
> 111.2 小时（物理不可能）——修复后断言落在"降雨≤天数×24"这种物理不变量上，
> 而不是某个具体数值；MinIO 假 up 是"进程活但所有写操作 403"，靠 health 里区分
> TCP 探测和实际后端才暴露。

**Q：并发上来怎么扩展？**

> 当前是单机单进程，诚实说三处天花板和方案：① BM25 在 Python 内存里算（千级
> chunk 可用），到十万 chunk 换 PG 全文索引（检索器接口不变）；② uvicorn 单进程
> 换 gunicorn 多 worker + PG 连接池；③ 会话/缓存已在 Redis。Agent 层无状态
> （状态在 ctx 和 DB），横向扩展主要受 LLM API 吞吐限制而不是自身。

### 3.6 安全与合规

**Q：用药建议的合规怎么保证？**

> 规则引擎按登记信息四维校验：作物、防治对象、生长阶段、安全间隔期——任何一个
> 不匹配就拦截，拦截理由逐产品展示给用户（"没登记在你种的作物上"而不是含糊的
> "不可用"）。剂量一律显示标签原文，系统不生成数字。抗性管理：同一作用机理组
> （FRAC/IRAC）连续使用超限会告警。这些校验对 LLM 生成的文本同样生效（输出护栏
> 剔除命中拦截规则的句子）。数据层同样有纪律：不编造登记证号、登记信息只增不减
> （升级走集合并集，收窄必须人工复核）。

**Q：还有哪些安全设计？**

> bcrypt 密码哈希（含 72 字节边界处理）、JWT、图片上传剥离 EXIF（农户照片的 GPS
> 不泄露）、越权访问一律 404（不泄露资源存在性）、上传类型与大小白名单、
> 登录失败话术防账号枚举。

### 3.7 数据

**Q：训练数据/知识数据从哪来？**

> PlantVillage 公开数据集（39 类 5.5 万张，从 ModelScope 下载）训练分类器；
> 知识库按公开植保常识由 LLM 辅助整理成结构化条目，来源分三级标注
> （official/academic/community）、逐条带"待补充文献出处"标记和 review_status。
> 我的立场是：**知识内容错不影响用药安全**（用药走独立规则引擎校验登记数据），
但内容准确性仍靠审核流兜底——数据模型支持，审核动作是待办。

## 5. 三个杀手锏故事（STAR 结构，主动往对话里带）

### 故事一：评测驱动——hit@3 从 81% 到 97% 的每一步都有归因

**S**：知识库只有 36 篇文档时检索质量无法证明。**T**：让"检索变好了"可量化。
**A**：先建 36 条口语化评测集（农户真实问法→期望病害），然后每次改动跑一遍：
发现别名断裂（西红柿/土豆不在映射，hit@1 67→72%）→ 语料扩充 3 倍后**反而跌到
61%**（近似病害互相稀释，这不是退化是考题变难）→ 加标题命中第三路 RRF →
发现原薄文档被新条目挤出 → 建"文档增厚"机制 → 69%/97%。
**R**：最终 69%/97%，且此后每次知识库改动都有回归防线。**金句**：评测集是尺子，
没有尺子的优化都是玄学。

### 故事二：桌面弹窗调查——测量方式先于结论

**S**：用户电脑不停弹命令行窗口，无法使用。**T**：找到原因。
**A**：第一版探针数 conhost 进程增量——结论被调用者自己污染；第二版想验证可见性
又漏了 Windows Terminal 这个宿主——两次方向相反的错误结论。第三次换成**枚举当前
会话所有可见的控制台类顶层窗口**（不依赖任何假设），一次单变量对照实验定案：
DETACHED_PROCESS 让 PG 自建控制台产生 4 个窗口，CREATE_NO_WINDOW 是 0。
**R**：修复+启动自检+看门狗退避熔断。**金句**：查不出来时先怀疑测量方式；
"无法确证"也是一个需要证据的结论。

### 故事三：3 天降雨 111.2 小时——物理不变量抓静默失效

**S**：不带 field_id 查天气，系统把**所有地块**的记录加总，3 天累计降雨 111.2 小时
（物理不可能）。更糟的是这个污染会流进风险打分（12/30 条病害的降雨条件恒满足）。
**A**：根因是 `if field_id:` 空值时完全不过滤；修复后把断言落在**物理不变量**
（降雨≤天数×24）而不是具体数值上——数值会随日期变，不变量永不假红。
**R**：顺带建立了"数据覆盖体检"（哪些病害无登记药），后来用户撞到的每个数据缺口
都能据此快速定位。**金句**：静默失效不报错只是不对，防线是全链路留痕+体检端点。

## 6. 坦诚应对：弱点与答法

| 可能被质疑 | 坦诚回答 |
|---|---|
| "诊断准确率怎么证明？" | 端到端 ground truth 评测集是我认定的最大欠账，已有检索 hit rate 和分类器逐类报告；下一步是 50 条"症状→期望病害"的标注评测。**主动给出计划比回避强**。 |
| "数据是 LLM 编的吧？" | 是 LLM 辅助整理、来源分级标注、逐条"待补充文献出处"、review_status 审核流在数据模型里齐备；且**用药安全不依赖知识内容**——走独立的登记数据规则引擎。 |
| "单机项目，没有真实用户？" | 按"敢给别人用"标准做了：浏览器 e2e、降级可见、越权测试、数据升级机制；列"还没做的"（压测、多租户、审核后台）证明边界意识。 |
| "为什么不用现成的Agent平台/Dify？" | 见 3.1 第一问——确定性流程要可观测性，且自研后对 Function calling、路由、工具白名单的理解是自己的一手经验（可以讲路由裁剪静默跳过新节点的坑）。 |
| "前端为什么不用 Vue/React？" | 零依赖 SPA 是刻意选择：农户场景要求"双击就能用"，且把时间花在后端/LLM 层。前端契约、DOM 交叉核对、真实浏览器 e2e 一套没少。若岗位强要求前端栈，强调可迁移。 |
