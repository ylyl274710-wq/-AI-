# 实施问题清单

> 对应《农业病虫害智能诊断与农事决策 Agent 技术路线方案》
>
> 本文档记录三部分内容：
> 一、**原技术路线文档本身的问题**（只读文档就能发现的，实施前必须澄清）
> 二、**实施过程中暴露的真实缺陷**（写完代码、真跑起来才暴露的）
> 三、当前状态与待验证项
>
> 所有缺陷都标注了「是产品缺陷还是我的实现缺陷」—— 这两者的修复方向完全相反，

## 一、原技术路线文档本身的问题

### A 类：不澄清就无法开工（4 项）

#### A1. 知识库的表结构只有一句话

文档第五章写「agricultural_knowledge：农业知识文档及元数据」，然后直接进入 RAG 检索
流程。但**检索的最小单位是 chunk，不是文档**——没有切块表，向量存哪里、元数据
怎么冗余、一篇文档被切成几块，全部无从落地。

**处理**：补三张表。原文档缺的是：

| 表 | 为什么必须有 |
|---|---|
| `knowledge_chunks` | 切块 + 向量列 + 冗余检索元数据。没有它，RAG 无从实现 |
| `disease_records` | 病害虫害标准条目 + **结构化发生条件**（见 A2） |
| `knowledge_sources` | 来源溯源。文档难点 12 要求「每条知识可追溯」，但没说存哪 |

另外文档提到的 `pesticide_active_ingredients` 在第五章表清单里也漏了，同样补上。

#### A2. 「发生条件」没有数据形态

文档难点 7 说「根据知识库中的发生条件计算风险等级」，但**没定义发生条件长什么样**。
是一段自然语言（「高温高湿易发病」）还是结构化字段？

**这是整份文档里最关键的一处模糊**：如果存自然语言，就只能让模型读天气描述再自己
判断风险等级——而模型判断不可复现，同一份天气数据两次调用可能给出不同结论，也没法
向农户解释「凭什么是高风险」。

**处理**：定义成可计算的结构化字段：

```json
{
  "temp_min": 20, "temp_max": 30,
  "humidity_min": 85, "rain_hours_min": 4,
  "duration_days": 2, "wind_max": 6
}
```

`services/weather.py::assess_risk()` 逐项打分归一化。这样风险等级是纯函数输出，
能写进测试、能把「平均气温 24.3℃ 落在 20~30℃ 适宜区间」直接摆给农户看。

#### A3. 置信度从哪里来 —— 文档没交代，而默认做法是错的

文档多处要求「置信度不足时要求用户补充照片」，但**没说置信度怎么算**。

多模态大模型可以「自报」一个置信度，但那是**不可校准**的：模型说 0.9 并不代表 90%
正确，同一个模型在不同问题上还会系统性地高估或低估。拿它当闸门阈值，等于把一个
未经验证的数字当成安全边界。

**处理**：改成可计算的置信度，三个分量加权：

```
score = 0.45 × margin + 0.30 × agreement + 0.25 × coverage
```

- `margin`：结论与最强竞争候选的差距（不是简单取检索前两名——见 B4）
- `agreement`：多张照片/多次识别的结论是否一致
- `coverage`：命中的知识覆盖了多少查询意图

每个分量都可复算、可写进论文做消融实验。

#### A4. Agent 编排框架选型未定

文档提到「LangGraph 或自定义工作流」，但没说选哪个。这个选择影响很大：

- **LangGraph**：图结构灵活，但调试时调用栈深、出错定位难，且引入重依赖
- **自定义状态机**：节点是普通方法，可断点、可单测、可逐节点记耗时

**处理**：选自研有限状态机（`agent/fsm.py`）。理由：本项目的流程是**确定的**
（诊断固定 9 个节点），不需要动态图；而可观测性（每个节点的耗时、工具调用、
失败原因）比灵活性重要得多——文档难点 6「Agent 失控」和难点 13「结果无法验证」
都指向同一个诉求：**出问题时要能说清是哪一步出的**。

配套做了节点级工具白名单 `TOOL_POLICY`：越权调用直接抛 `ToolNotAllowed` 并留痕。

### B 类：能开工但会埋雷（7 项）

#### B1. 图片被放在 diagnosis_records 里，但一次诊断可以传多张

文档难点 1 明确要求「用户补充叶片正反面 / 整株 / 病斑近照」，说明一次诊断有多张图，
是一对多关系。原文档把图片字段写在 `diagnosis_records` 上。

**处理**：拆出 `diagnosis_images` 表，带 `shot_type` 字段区分拍摄角度——这个字段是
闸门 A 判断「还缺哪张照片」的依据。

#### B2. 农药登记信息里根本没有「使用阶段」

文档要求规则引擎校验「生长阶段是否适用」。但**农药登记信息本身不含这个字段**——
登记的是作物、防治对象、剂量、安全间隔期，没有「苗期能不能用」。

**处理**：`applicable_stages` 明确标注为人工标注字段，并在 API 响应里带
`data_caveat` 免责声明。**不能让前端把人工整理结果当成官方登记信息展示给农户。**

#### B3. 天气「作为辅助特征」—— 但没说辅助到什么程度

文档难点 7 的表述容易被理解成「天气可以参与诊断结论」。这是危险的：天气说
「适合霜霉病发生」是概率，说「你的番茄得了霜霉病」是断言，混在一起农户会照着
天气预报去打药。

**处理**：定死一条边界——`/weather/risk` 返回的每条只带「建议巡田 / 多留意」这类
措辞，**不出现任何用药指令**，且不返回置信度、不返回 top1。前端展示时必须与
「诊断结果」在视觉上明显区分。

#### B4. RRF 融合缺少归一化 —— 会导致闸门永远拦截

文档建议用 RRF（Reciprocal Rank Fusion）融合向量与关键词两路结果，方向正确。
但 RRF 的原始分数量纲是 `Σ weight/(k+rank)`，`k=60` 时 rank1 只有 `1/61 ≈ 0.0164`，
**rank1 与 rank2 的绝对差仅 1.6%**。

如果直接拿原始分算「分差」再和阈值比较，实测结果是 `margin ≈ 0.004`、
`coverage = 0.333`（一篇文档一个 chunk 导致恒为 1/3），加权总分 0.286，
**永远够不到 0.55 的阈值 —— 闸门 A 变成「永远拦截」，所有诊断都返回
「信息不足」。**

**处理**：引入理论最高分 `max_fused_score() = Σweight/(k+1)` 做归一化，两个分量
都落回 `[0,1]` 且与 `k`、通道数无关，阈值可以跨配置复用。

#### B5. 没有对话历史表

文档第五章表清单里没有 `chat_messages`。但没有它，「接着上次继续问」「历史会话列表」
这两个基础交互都无从实现。

**处理**：补 `chat_messages` 表，并把执行轨迹、工具调用、引用来源一并存下来，
便于事后复盘「为什么给出这个回答」。

#### B6. 没有反馈闭环

文档难点 13 说「结果无法验证」，但没给出解决路径。

**处理**：`diagnosis_records` 加 `feedback_resolved` / `feedback_note` / `feedback_at`；
`farm_tasks` 完成任务时收一句 `feedback`。这是唯一能积累真实标注的来源——
既能算准确率，也是后续做 badcase 库的原料。

#### B7. 作物与病害是多对多，文档按一对一设计

「黄瓜白粉病」同时登记在黄瓜、番茄、辣椒上（同一个病原，多种作物感病）。
如果按「一条知识属于一个作物」建模，按番茄检索时这条知识会被**静默排除**——
不报错，只是召回少了，属于最难排查的一类 bug。

**处理**：`disease_records.crop_names` 用 JSONB 数组 + GIN 索引，检索时用数组包含
判断；空数组代表通用植保知识，任何作物都保留。

### C 类：顺序问题（1 项）

#### C1. 先做前端还是先做 Agent

文档的章节顺序是「前端 → 后端 → 数据库 → RAG → Agent」，按这个顺序做，会在
Agent 逻辑还没定型时先冻结 API 契约，后续几乎必然返工。

**处理**：先打通「种子数据 → RAG → 规则引擎 → Agent → HTTP 接口」的后端闭环，
再用脚本级 + HTTP 级双重冒烟验证，最后做前端。前端只消费已经验证过的契约。

## 二、实施过程中暴露的真实缺陷

> 以下全部是**跑起来才暴露**的问题。分两类标注：
> **[产品缺陷]** = 代码逻辑与设计意图不符，改代码
> **[我的实现缺陷]** = 我写错/写漏，改我的写法

### 严重：接口直接 500（3 个）

#### D1. 三张表缺软删除字段，但代码按它过滤 **[产品缺陷]**

`FarmTask`、`CropGrowthRecord`、`DiagnosisRecord` 三个模型只继承了
`PKMixin + TimestampMixin`，**没有 `SoftDeleteMixin`**，但
`api/v1/farm.py`、`api/v1/diagnosis.py` 共 6 处按 `deleted_at.is_(None)` 过滤。

```
AttributeError: type object 'DiagnosisRecord' has no attribute 'deleted_at'
```

**修复方向**：改模型加字段 + 迁移，**不是**删掉过滤条件。理由：软删除对农事记录有
真实价值——任务表带 `diagnosis_id`，硬删等于抹掉那次诊断的后续动作，之后复盘
「建议了巡田，农户去没去」就没依据了。

**新增迁移**：`23faafef2e86`、`179ddf3cde0a`。

#### D2. 调用了不存在的服务方法 **[我的实现缺陷]**

`farm.py` 里写了 `WeatherService.get()` / `.to_dict()` / `.candidate_diseases()`——
三个方法都不存在。真实接口只有 `get_recent(field_id, lat, lng, days)`，返回
`list[WeatherSnapshot]`；`to_dict()` 是 `RiskAssessment` 上的方法，不是服务上的。

根因是我凭记忆写调用，没先读 `weather.py`。**教训：跨模块调用前先 grep 签名。**

#### D3. 漏导入导致 NameError **[我的实现缺陷]**

`farm.py` 用了 `FieldOut` 但没导入。这类错误在 Python 里只有请求打到那个端点才暴露。

**配套改进**：把 `pyflakes` 纳入日常检查——它能直接抓出 undefined name，
比等运行时 500 快得多。

### 严重：功能静默失效（3 个）

#### D4. 视觉降级分支不组装 `answer`，前端弹空白气泡 **[产品缺陷]**

`_node_diagnose` 里「未配置视觉模型」的分支只填了 `ctx.answer_sections`，
**没填 `ctx.answer`**。而 HTTP 响应只对外暴露 `answer` 一个字段，结果是：

```
状态码 200，state=needs_more_info，answer=""   ← 用户看到的是一个空白气泡
```

真实原因（没配视觉模型）躺在 `answer_sections` 里，前端不主动解析就永远看不到。

**修复**：补齐 `ctx.answer`。**对外只暴露一个字段的接口，就必须把它填满。**

#### D5. 视觉降级分支不落库，`diagnosis_id` 为 null **[产品缺陷]**

同一分支直接 `return NEEDS_MORE_INFO`，跳过了 PERSIST 节点，后果：

- 这次提问完全没记录，对话历史里整段缺失
- 前端拿不到 `diagnosis_id`，**无法把补拍的照片关联回上一次提问**
- 将来接入视觉模型后，无法回答「当初有多少张图因为没配模型而浪费了」

#### D6. 闸门 A 拦截不落库，两个状态成了死代码 **[产品缺陷]**

闸门 A 在 RETRIEVE 节点提前终止（`rejected` / `needs_more_info`），而
`_node_persist` 里恰好有一段「如果 confidence 不达标就记成
`ST_NEEDS_MORE_INFO`」的逻辑——**这段逻辑永远执行不到**，因为流程根本走不到
PERSIST。

判断依据：`ST_REJECTED` 和 `ST_NEEDS_MORE_INFO` 这两个状态**被定义出来了**，
说明设计意图就是要记录这类情况。定义存在但永远写不进去 = 死代码。

**修复**：拦截时也调 `await self._node_persist(ctx)` 再终止。

### 严重：视觉链路静默失效（1 个，本轮新发现）

#### D21. 视觉提示词定义了却从没传给模型，且拍摄部位信息完全没用上 **[产品缺陷]**

这是**最典型的一类「不报错、只是结果不对」缺陷** —— 而且因为当前没有配 Key
（`vision_enabled=False`），整条视觉链路从没被真正执行过，所以它一直没暴露。

三个问题叠在一起：

1. **`VISION_SYSTEM` 是死代码。** 项目里精心写了植保专家角色 + 安全规则 +
   照片质量评估要求，但 `tool_impl.vision_diagnose` 自己拼了一个 4 行的简易提示词，
   而且 `LLMClient.vision()` **根本没有 `system` 参数** —— 连传都传不进去。
   模型不知道自己的角色，也不知道安全规则。
2. **`VISION_SCHEMA` 也是死代码，而代码正在按它解析。**
   `vision_diagnose` 下面的代码读取的正是 `image_quality` / `candidates[].name` /
   `per_image[].top1` / `missing_shots` / `notes` —— 这些字段名全部来自
   `VISION_SCHEMA`。但提示词里没告诉模型要按这个结构输出，
   只开了 `json_mode=True`。**结果：即便配上 Key，`candidates` 也大概率是空数组，
   而且不报错、不告警，只是回答里没有诊断结论。**
3. **`ctx.image_shot_types` 完全没用上。** 上下文里明明带着每张图的拍摄部位
   （叶正面/叶背面/整株/病斑特写），但没告诉模型。而 `VISION_SCHEMA` 要求它
   输出 `missing_shots`（还缺哪个角度）—— 模型不知道已经拍了什么，只能瞎猜。

**修复**：给 `LLMClient.vision()` 加 `system` 参数；`vision_diagnose` 传入
`VISION_SYSTEM` 并把 `VISION_SCHEMA` 拼进用户提示词；同时把每张图的拍摄部位
按「图1：叶片正面」的形式告诉模型。

**为什么 HTTP 冒烟测试（79 项）抓不到它**：视觉分支只在 `settings.vision_enabled`
为真时进入，没有 Key 就永远走降级分支。**测试覆盖不到的分支 = 没写过的分支。**
因此补了 `backend/scripts/check_vision_wiring.py` —— 它替换掉真正发请求的那一层，
直接检查发给模型的消息体，不需要 Key 就能跑。

> 一个附带的坑（**我在新增拍摄部位标注时特意避开的**，不是已存在的 bug）：
> 原循环里 `data_urls.append(...)` 在 `try` 内、失败的图会被 `continue` 跳过，
> 如果事后再用 `enumerate` 的下标去回填 `image_shot_types`，坏图之后的标注
> 会**整体错位一位**。所以拍摄部位必须和图片在同一个循环里成对收集。
> 探针里专门加了一条「不应出现『叶片背面』」来守住这个位置。

### 中等：状态与字段语义错位（3 个）

#### D7. 诊断状态靠 confidence 反推，有两个盲区 **[产品缺陷]**

原逻辑：`confidence.rejected → ST_REJECTED`，`not confidence.passed →
ST_NEEDS_MORE_INFO`。两个盲区：

1. 闸门 A 提前终止时走不到 persist（见 D6）
2. 视觉降级分支发生在 DIAGNOSE 节点、**此时还没有 confidence**，只能被记成
   `succeeded` —— 明明是「需要用户补充信息」，却记成成功。做数据统计时完全失真。

**修复**：改为直接按 `ctx.state` 映射。任何终止点只要在落库前把 state 设对，
状态就一定正确，不需要每个分支各写一套判断。

#### D8. `TaskOut` 缺 `feedback` / `done_at` **[产品缺陷]**

农户完成任务时填的反馈写进了库，但响应模型里没有这两个字段 —— 前端「已完成」
列表看不到当时反馈了什么，这个字段等于白存。而它是判断「Agent 的建议到底有没有用」
的唯一真实信号。

#### D9. 咨询意图被误记成「信息不足」 **[产品缺陷]**

`_node_persist` 不看意图就按置信度写状态，导致「这两天天气怎么样」这类咨询
（用户明明拿到了完整回答）被记成 `needs_more_info`。后续统计「有多少比例没答上来」
会完全失真。

**修复**：状态降级只在 `ctx.intent == "diagnosis"` 时生效。

### 工具链自身的问题（5 个，都是我的实现缺陷）

这几个都不影响线上功能，但会**让人误判线上功能有问题**，所以单列。

| # | 问题 | 现象 | 根因 |
|---|---|---|---|
| D16 | 块注释里写 glob 路径导致注释提前闭合 | `node --check` 报 `Unexpected token ']'`，位置指向一个**完全合法**的正则字面量 | 注释里写了 `/x/*/y` 这种路径，其中的「星号+斜杠」被当成块注释结束符。注释在 `/x/` 处就断了，剩下的文字变成代码，开启一个**永不闭合的模板字符串**，一路吞到几十行之后才报错。**这个坑我连踩四次**（见 D23，第 4 次是在专门解释它的注释里） |

`frontend/tools/scan-block-comments.mjs`（统计每个 js 文件里块注释开符与闭符是否配平），
比等 `node --check` 报错定位快得多。

#### D23 的修复：三个工具共用一个词法器

D23 的正解不是「把注释改得不用写那个路径」，而是**让检查器正确识别行注释**——
因为代码本身没错，错的是尺子。

修的时候顺手做了两件对的事：

1. **复用 `js-lex.mjs` 的状态机，而不是在配平器里再写一份**。
   两份状态机一定会漂移，到时候两个工具给出互相矛盾的结论。
   现在 `blankComments(src, stats)` 多接受一个计数器，`blockCommentStats(src)`
   就是它的一层薄封装。
2. **补了永久负向自测 `frontend/tools/selftest-js-lex.mjs`（18 项）**。
   「扫到 0 个问题」有两种可能——代码真的没问题，或者尺子坏了。
   不区分这两者的检查器等于没有检查器。自测覆盖：
   行注释 / 字符串 / 模板串 / 正则字面量里的符号（**都不该计入**）、
   块注释提前闭合与未闭合（**都必须抓到**）、等长替换不破坏行号、
   以及 core.js 那个「正则里带引号」的真实陷阱。

#### D24 的教训：桩要「响亮地失败」

DOM 桩对不认识的选择器**抛错**，而不是返回 null。这个设计当场就起作用了 ——
我自己写测试时用错选择器，立刻报出来并指出原因，而不是让我去追一个
「`querySelector` 返回 null 导致后续 TypeError」的假线索。

**结论：检查工具的默认行为应该是「不会就喊」，不是「不会就沉默」。**


### 严重：基础设施被自己的脚本反复杀死（2 个）

#### D19. 用 `taskkill /F /IM <镜像名>` 停服务，会杀掉别人的同名进程 **[我的实现缺陷]**

```python
def pg_stop():
    run(["taskkill", "/F", "/IM", "postgres.exe"])     # ← /IM 是按镜像名杀全局
def minio_stop():
    run(["taskkill", "/F", "/IM", "minio.exe"])
```

`/IM` 会杀掉**系统上所有**叫这个名字的进程 —— 包括另一个 serve 进程正在托管的、
以及用户自己项目里的。日志里的证据是 PostgreSQL 子进程反复以
`0xC000013A`（STATUS_CONTROL_C_EXIT）死亡，随后 postmaster 反复
`all server processes terminated; reinitializing`。

**修复**：一律按 PID 或端口精确定位。PG 用 `pg_ctl -D <PGDATA> -m fast stop`
（只认自己数据目录里的 `postmaster.pid`），兜底改成按端口查 PID 再 `taskkill /PID`；
MinIO 改成按 PID；Redis 本来就用 `redis-cli -p <port> shutdown`，天然是精确的。

#### D20. 多个 `serve` 进程并存，互相杀对方的服务 **[我的实现缺陷]**

实测同时跑着**三个** `serve` 进程（一个是我 1.5 小时前起的、被我 `TaskStop` 后
**只杀掉了 bash 外壳、python 本体成了孤儿还活着**；另外两个是后来的）。
每个 `serve` 的 `finally` 都会执行 `cmd_down()`，而 `cmd_down` 当时用的是
`taskkill /F /IM` —— 于是**任何一个 serve 退出，都会把另外两个正在托管的 PG 一起杀掉**。

**修复（三条一起上，缺一不可）**：
1. **单实例锁** —— `_infra/logs/serve.lock` 记录 PID，第二个 serve 直接拒绝启动并报出占用者 PID；
2. **服务归属记录** —— `_STARTED` 记下本进程实际启动过哪些服务，`serve` 退出时只停这些
   （用户自己开着的 PG 不该被我们顺手杀掉）；
3. **陈旧锁自愈** —— 锁里的 PID 已不存在时自动覆盖，否则崩一次就再也起不来。

**另外补了 `CREATE_NO_WINDOW`**：`run()` / `run_detached()` / `netstat` / `tasklist` /
`taskkill` / `initdb` 全部加上。当时我写的是「我没能证明它是弹窗的原因」——
**那句话后来被推翻了，见 D22：弹窗的真正原因正是启动标志用错了。**

#### D22. `DETACHED_PROCESS` 让 PostgreSQL 自己弹 4 个终端窗口 **[我的实现缺陷]**

**这是「桌面不停弹命令行运行框」的真正原因**，也是把用户的电脑搞到没法用的原因。

**现象**：用户报「现在一直在弹命令行窗口，导致电脑没法运行了」。

**根因链条**（每一环都有实测支撑）：

1. `pg_start()` 用 `detached()` 启动 postgres，标志是
   `CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS`。
2. `DETACHED_PROCESS` 的语义是「系统**不给**这个进程控制台」。
3. PostgreSQL 在 Windows 上发现自己没有控制台时，会自己调 `AllocConsole()` 建一个。
4. Windows 11 的默认终端是 **Windows Terminal** —— 任何进程新建控制台，
   系统就**新开一个终端窗口**。postmaster + 后台进程一共 4 个 → 一次启动弹 4 个窗口。
5. 看门狗每 15 秒检查端口，服务掉线就重启 → **窗口持续弹**。
6. 反过来说，那个**可见**的窗口一旦被关掉，控制台销毁 → 控制台里所有进程收到
   `CTRL_CLOSE_EVENT` 并以 `0xC000013A`（STATUS_CONTROL_C_EXIT）退出 ——
   **这正是日志里反复出现 `0xC000013A` 的另一半原因**（D19/D20 是人为杀的，
   这条是自己被窗口关闭带走的）。

**单变量对照实验**（`scripts/_probe_console_flags.py`，判据是
「所有可见的『控制台类』顶层窗口数量」，不限定宿主进程）：

| 启动标志 | 新增可见控制台窗口 |
|---|---|
| A. `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP`（修复前） | **4 个** |
| B. `CREATE_NO_WINDOW`（修复后） | **0 个** |

**修复**：`infra.py` 新增 `spawn_hidden()`，统一用
`CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`，`pg_start` / `redis_start` /
`minio_start` 三处全部改用它。`CREATE_NO_WINDOW` 给的是**隐藏**控制台，
进程有控制台可用就不需要自建 → 一个窗口都不弹。

**两道防线，防止复发**：

1. **启动后自检** —— `cmd_up()` 结束时枚举一次可见控制台窗口，不为 0 就在日志里
   大声报出来（`visible_console_windows()`）。这类回归不报错、不写日志、
   测试也测不到，只能靠自检。
2. **看门狗退避 + 熔断** —— 连续失败按 15s → 30 → 60 → 120 → 240s 退避，
   连续 5 次失败后**熔断**、不再自动重试。原来的看门狗是「每 15 秒重启一次、
   永远不停」，这正是把「一个小故障」放大成「用户无法使用电脑」的放大器。

**验证**：`infra.py serve` 起来后日志出现
`[infra] 自检通过：未产生任何可见控制台窗口`，同时外部探针独立确认
可见控制台窗口为 0 个（修复前 PG 启动会新增 4 个）。

**我在这条上犯的两次方法错误**（比 bug 本身更值得记）：

- **v1 探针**：数 `conhost.exe` 增量就下结论「PG 创建了 4 个控制台，
  这就是弹窗来源」——**没有验证窗口是否可见**。
  但 `CREATE_NO_WINDOW` 同样会产生 conhost，它的窗口却是隐藏的。
  「有控制台」≠「有可见窗口」。
- **v2 探针**：想补上可见性验证，判定逻辑却只统计了**conhost 进程拥有的**窗口，
  漏掉了真正的宿主（Windows Terminal 的 `CASCADIA_HOSTING_WINDOW_CLASS`），
  于是得出「PG 不是弹窗来源」——**方向完全反了**。
  这是**测试缺陷**，产品行为没变，是我量错了。修尺子，不是修产品。

两次都是「拿一个自己没验证过的指标下结论」。最后改成
「枚举所有可见控制台类窗口，不限定宿主进程」才拿到可信数据。

#### D25. `/health` 报 `minio: up`，而 MinIO 实际一个字节都存不进去 **[产品缺陷]**

**现象**：MinIO 进程活着、9000 端口在听、`/health` 报 `"minio": "up"`，
但所有 S3 操作都被拒绝：

```
WARN: No valid license found, running in offline mode. All S3 operations are denied.
...
S3 operation failed; code: AccessDenied, message: Access denied.
No license is installed. Please install a valid license using 'mc license update'
```

**先分清哪部分不是问题**：MinIO 开源版已于 2025 年归档，官方只保留商业版
Aistor 的构建，而 Aistor 要 license。所以「MinIO 不可用」在本机是**常态**，
不是意外。`services/storage.py` 对此的处理是**正确**的 —— 探测失败就降级到
`LocalStorage`（本地磁盘 + `/media` 静态目录），业务功能不受影响。
实测确认：

```
构造 MinioStorage：失败 AccessDenied
get_storage() 实际选中：local  →  E:\...\storage\media
```

**真正的问题是我们把这次降级藏起来了**，两处：

1. **`/health` 的 `minio` 字段只做 TCP 探测**（`_minio_status()`）。它的注释
   解释了为什么不用客户端库 ping ——「避免把『服务活着但密码错了』误报成
   『服务挂了』」。这个理由本身是对的，但它把错误翻到了另一个极端：
   **「进程活着但功能全废」被报成了 `up`**。
2. **前端本来就有对应的提示条，却永远不会触发**：

   ```js
   if (h.minio !== 'up') msgs.push('图片存储不可用');   // ← 恒为 false
   ```

   于是降级在用户侧完全不可见。

而 `api/v1/health.py` 的模块注释里恰恰写着：

> 「每一个都能降级……系统看起来能跑，但用的是假数据或兜底算法……
>  所以 /health 必须把『哪些依赖真的活着、当前是不是降级模式』明确报出来，
>  前端要把它显示在页面上，而不是藏在日志里。」

**设计意图完全正确，实现漏了一环。** 这是最值得记的一类缺陷：不是想错了，
是**想到了但没做到**，而且漏掉的恰好是「让用户知道」—— 也就是这道防线的全部意义。

**修复**：

- `HealthOut` 增加 `storage` 字段（对象存储的**实际后端**：`minio` / `local`），
  与 `minio`（TCP 连通性）分开。两个信息都有用，但回答的是不同问题。
- `_storage_backend()` 的 `except` 必须 `logger.warning`。
  ★ 这条不是随手加的：第一版我写的是裸的 `except Exception: return "unknown"`，
  结果它把我自己漏写的 `import get_storage`（`NameError`）也吞成了 `"unknown"` ——
  表面看像「探测失败」，实际是「代码写错了」。
  **兜底可以宽，但兜底必须说话。**
- 前端改为按 `storage` 判断，两个分支都覆盖：
  `storage === 'local'` → 「对象存储不可用，图片改存本地磁盘」；
  `storage === 'minio'` 且 `minio !== 'up'` → 「图片存储不可用」。
- 顺手修了一个文案 bug：提示条结尾原来固定是
  「在 `.env` 里配置 API Key 后重启即可启用」——
  可缓存/存储挂了你让人去配 API Key，是驴唇不对马嘴。
  现在只在**配置类**提示出现时才加这句。

**回归测试**：`check-frontend-runtime.cjs` 加了 3 条断言，用**改造过的 fixture**
覆盖三种输入（`local` / `minio+端口通` / `minio+端口断`）。

★ 为什么不直接断言「一定出现对象存储提示」：fixture 里的 `storage` 会随
MinIO 好没好而变化，那样写在 MinIO 修好之后会**假红**。
**断言要落在「逻辑」上，不能落在「当前环境值」上。**

★ 写这组断言时还踩了一个 fixture 的坑：`fixtures` 的 key 是**文件名**
（`'health'`），`ROUTES` 才是路由（`'GET /health'`）。我一开始按路由写 key，
`Object.assign` 静默变成了「只用 patch 当 fixture」—— 测试照样在跑，
其中两条还「通过」了，但**通过的原因是错的**（用的仍是磁盘上那份 fixture）。
两套 key 空间混用不会报错，只会让测试假装在工作。

#### D26. CSS 覆盖了 `[hidden]`，登录后登录门不消失、主界面进不去 **[产品缺陷 · P0]**

**现象**（真实浏览器首次运行就抓到）：

```
[FAIL] 主界面隐藏                  ← 未登录时 #app 也被判定为「可见」
[FAIL] 登录后登录门隐藏            ← 登录后 #gate 还在
[FAIL] 页面 home 渲染出内容 —— children=True, textLen=6
```

DOM 层**一切正常**：`#whoName` 确实渲染出了「演示农户」，六个页面也都
渲染了内容。**但截图里看到的一直是登录页** —— 登录门盖在界面上，
用户登录成功后根本进不去主界面。

**根因**：

```css
.gate { display: grid; ... }     /* style.css:125 */
.app  { display: flex; ... }     /* style.css:245 */
/* 全文件没有任何 [hidden] 规则 */
```

浏览器默认样式表里有 `[hidden] { display: none }`，但它属于 **UA 样式表**，
而层叠规则是「作者样式表 > UA 样式表」——**这与选择器优先级无关**。
所以只要作者样式表里给同一个元素写了 `display`，`element.hidden = true`
就完全失效。`.gate` 和 `.app` 恰好都写了 `display`。

**修复**（业界标准做法，normalize.css 同款）：

```css
[hidden] { display: none !important; }
```

**一条规则修好了 4 项失败。**

**为什么 78 项 DOM 桩断言全绿也没抓到**：

桩里 `element.hidden = true` 就是隐藏了 —— 它没有 CSS 引擎，
`hidden` 只是它自己维护的一个属性。**这是「桩测不到 CSS」最典型的例子**，
也是必须补真实浏览器这一层的直接理由。

★ 这个缺陷的**伪装性**值得单独说：它不报错、不打日志，
在控制台里查 `document.getElementById('app').hidden` 返回的是 **`true`**（正确），
DOM 结构也全对。**只有「看起来对不对」能发现它 —— 也就是只有截图或
真实渲染能发现它。** 这也解释了为什么它能在 78 项桩断言 + 5 个静态检查
全绿的情况下活到今天。

**同时暴露的次要问题（未修，记录在案）**：

- 提示条文案「两类问题会同时出现」时二选一 → 已修（见 D25 的修复段）
- 窄屏（375px）下顶栏被挤：品牌副标题换行、「演示农户」竖排；
  提示条本身占掉约 6 行首屏高度。功能没问题，是体验问题。

**我的测试自己错了 2 项**（老规矩，分清产品缺陷与测试缺陷）：

老人模式那两条断言我按「点一下就是开启」写，红了两次。实际
`core.js` 里是 `store.setElder(me.elder_mode !== false)` ——
**demo 用户的老人模式默认就是开启的**，第一次点击是「关掉」。
断言改成与初始状态无关的不变量：**开着的字号 > 关着的字号**。

#### D27. 天气的 provider 配置项是「空头支票」，填了不生效 **[产品缺陷]**

`config.py` 里有一组看起来完整的天气配置：

#### D28. 不带 `field_id` 查天气，会把**所有地块**的记录加在一起 **[产品缺陷]**

这个缺陷是**用户填完 API 配置、我重启后做验证**时撞见的 —— 不是测试跑出来的，
是「打开接口看一眼返回什么」撞出来的。

现象：`GET /weather/current?days=3`（不传 `field_id`）返回

```json
{"record_date": "2026-09-25", "rainfall_hours": 111.2, ...}
```

**3 天累计降雨 111.2 小时。** 3 天总共只有 72 小时。

根因在 `services/weather.py` 的 `get_recent()`：

```python
stmt = select(WeatherRecord).where(WeatherRecord.record_date >= since)
if field_id:                                   # ★ 空的时候完全不过滤
    stmt = stmt.where(WeatherRecord.field_id == field_id)
```

`field_id` 为空时**不是「不针对地块」，而是「不过滤」** —— 于是把库里
10 来个地块同一天的记录全捞回来，`summarize()` 再一 `sum`，就成了 111.2。

**为什么这个数字不能忍**（不只是难看）：

- 30 条病害里有 **12 条**的发生条件带 `rain_hours_min`（阈值 2~6 小时）
- 污染后这一项**恒为满足** → 风险分被系统性抬高
- 而且会一路传到**给农户看的文案**里：
  `满足：累计降雨 111.2 小时（需 ≥4 小时）`

农户看到这种物理上不可能的数字，整个风险提示的可信度就没了 ——
而 `/weather/risk` 在 `smoke_http.py` 里恰恰是**不带 field_id** 调的，必踩。

**修法**：把「哪个地块」当成**约束**而不是可选过滤，并且和 `_persist()`
写入时的语义严格对齐（`field_id=None` ↔ `field_id IS NULL`）：

```python
stmt = stmt.where(WeatherRecord.field_id.is_(None) if field_id is None
                  else WeatherRecord.field_id == field_id)
```

**回归断言刻意落在物理不变量上**（`rainfall_hours <= days × 24`），
而不是「等于某个具体数值」—— 后者会随日期和库里存量数据变化，
跑一次绿一次红，最后被人当噪声忽略。另外在**文案层**再兜一道：
风险理由里出现的「累计降雨 N 小时」也不许 > 72。

修复后：3 天 111.2 → **12.6**；7 天 **23.8**（上限 168）。

#### D29. 天气快照一旦写入就**永久过期**，窗口滑动但不会补新日期 **[产品缺陷]**

同一个函数，第二处：

```python
if rows:              # ★ 窗口里只要有任意一行，就整段返回
    return rows
```

后果是**永久过期**，不是「偶尔晚一天」：

```
第 1 天（09-25）调用 → 窗口 [09-23, 09-25] 为空 → 生成并写入 3 天
第 2 天（09-26）调用 → 窗口 [09-24, 09-26]，09-24/25 还在 → rows 非空
                     → 永远不生成 09-26
第 3 天（09-27）调用 → 窗口 [09-25, 09-27]，09-25 还在 → 还是那批
```

`record_date` 会一直停在第一次写入的那几天，界面上的「当前天气」
永远显示的是几天前的数据，**而且不会报错**。

★ 注意这**不只是 mock 的问题**：接真实天气源后同样命中 ——
「DB 里有就不刷新」等于**缓存没有过期机制**。`weather_cache_ttl_seconds`
这个配置项（1800 秒）在这里也是空转的。

**修法**：窗口内缺哪天补哪天，而不是「有任意一行就整段返回」。
`_mock_snapshot(days)` 也顺势改成 `_mock_snapshot_for(dates)` ——
收日期列表而不是天数计数，让「补缺失日期」这件事变自然，
省得调用方自己算偏移、差一天。

这个「补缺失日期」的位置，也正是将来调**真实天气源**的挂钩点。

#### D30. 意图识别提示词缺少「求解释 ≠ 求诊断」，LLM 覆盖掉了启发式里的判断 **[产品缺陷]**

**这条是「LLM 从降级模式切到真实模型」之后才暴露的** —— 之前
`llm_enabled=false`，走的是启发式，一直是绿的；填好 Key 之后
`smoke_http.py` 立刻红了一条：

```
[FAIL] 「为什么」类问题不误判成诊断 — intent=diagnosis
查询：黄瓜叶子为什么发黄？
```

看 `_heuristic_intent()`，它**明确处理过**这种情况，还写了注释：

```python
# ★ 「为什么 / 是什么原因 / 怎么回事」是在求解释，不是求诊断。
#   不单独区分的话，「黄瓜叶子为什么发黄」会因为含「发黄」被判成诊断，
#   接着被闸门 A 要求补拍照片 —— 用户问的是原因，不是让你看图看病。
if any(k in q for k in ("为什么", "什么原因", ...)):
    return "consult"
```

但 `_node_intent()` 是「启发式打底、LLM 覆盖」：

```python
ctx.intent = self._heuristic_intent(ctx)
if settings.llm_enabled and not ctx.has_images:
    data, _ = await llm.chat_json(...)          # ★ 成功就整条覆盖
    if data.get("intent") in INTENT_ROUTES:
        ctx.intent = data["intent"]
```

而 `INTENT_SYSTEM` 里 `diagnosis` 的定义是
「描述具体的作物异常症状（叶子有斑点、卷曲、烂根…）」——
「叶子发黄」完美命中，提示词里**没有任何一句**说「问原因该算 consult」。
模型按字面判成 `diagnosis`，是**提示词的锅，不是模型的锅**。

**这是产品缺陷**：代价不是「分类不准」，是**答非所问** ——
用户问「叶子为什么发黄」，系统回「麻烦再补拍一张照片」。

★ **判断依据：以哪个为准？** 启发式里的那段注释是**设计决策**
（有理由、有后果分析），不是随手写的兜底。LLM 把它覆盖掉，
等于把设计决策丢了。所以修的是**提示词**，让它承载同一条规则。

**修法**：在 `INTENT_SYSTEM` 里显式写出区分标准 ——
判断依据是「**用户想要什么**」，不是「句子里有没有症状词」：

- 「黄瓜叶子为什么发黄？」→ 问原因和原理 → `consult`
- 「黄瓜叶子发黄了，帮我看看是什么病」→ 要你判断 → `diagnosis`
- 出现「为什么 / 什么原因 / 怎么回事 / 咋回事 / 什么原理 / 如何预防」时
  **默认 consult**，除非用户另外明确要求判断病情

**顺带加的防线（防止矫枉过正）**：修「为什么被误判」时很容易写成
「看到『为什么』就 consult」，结果「辣椒叶子卷起来了，是不是病毒病」
也被判成 consult —— 那又错了。所以新加了
`backend/scripts/check_intent_llm.py`，**正反两个方向都有样例**：

```
反方向（求解释 → consult）  4 条
正方向（真诊断 → diagnosis）3 条
其他分类回归（pesticide/farm_analysis/task/consult）4 条
```

★ 它**故意不塞进 `smoke_http.py`**：跑一次要发 11 次模型请求，
塞进去会让 smoke 从「秒级」变成「分钟级」，最后没人愿意跑。
定位是「改了 `INTENT_SYSTEM` 或换了模型之后手动跑一遍」的专项检查。

★ 这个缺陷还说明一件事：**「降级模式全绿」不等于「真实模型可用」**。
配置 API Key 这个动作，本身就是一次**未测代码路径的启用** ——
和 D21（视觉提示词从没传进去）是同一类问题的两种表现。

#### D33. 「像网站不像 LLM 应用」的三项补强（2026-09-27，多轮记忆/流式/工具循环）

用户反馈：项目更像网站开发，没有体现 LLM 应用的工作。核实后的根因有三层：
对话历史**只写不读**（「接着上次问」是假的）；回答只推节点进度不推 token
（`llm.stream` 写好了但没人调用）；Agent 是固定管线，LLM 从不决定行为。
修复三项，各带一个实测暴露的真 bug：

1. **多轮记忆回灌**：run() 开始时把本会话最近 8 条 ChatMessage 读进
   ctx.history，进 INTENT_SYSTEM（追问识别：实测「那辣椒呢」单独看是病句，
   带历史后模型正确解析出作物=辣椒并转诊断路径）与 compose（不重复上一轮结论）。
2. **token 级流式**：SSE 路由注入 asyncio.Queue，compose 优先走
   `llm.stream()` 逐段推送 delta 事件（实测 278~519 个 delta/次）；
   一次性路由不注入队列，行为不变。★ 流出的是护栏前原文，final 才是
   剂量拦截后的权威版本，前端以 final 覆盖——「立刻看到字」与「输出合规」
   的折中，代码里有注释。
3. **Function calling 工具循环（consult 专属）**：TOOL_LOOP 节点让 LLM 自主
   决定调 search_knowledge / get_weather_risk / get_farm_context（实测自主
   选择 get_weather_risk 回答湿度问题）。循环只收集证据，回答仍由 compose
   生成（流式+护栏+三段式出口纪律不变）。留痕与 FSM 节点同一形态落库。

踩过的三个坑（两个是本轮引入的，靠实测轨迹抓出）：

- **路由裁剪沿主链找**（本轮引入，最严重）：`_next_in_route` 的兜底沿
  MAIN_CHAIN 找下一个节点，而 TOOL_LOOP 不在主链上——consult 路线
  CONTEXT 返回 DIAGNOSE 后被一路裁剪跳过 TOOL_LOOP 直达 COMPOSE，
  工具循环**从未执行**且无任何报错。修法：兜底改为「沿路线取当前节点之后
  的第一个」。教训：**给固定管线加新节点时，路由兜底逻辑必须同步审查**。
- **工具结果 JSON 序列化**（本轮引入）：`summarize()` 返回的 record_date
  是 date 对象，`json.dumps` 回灌给模型时炸出
  `Object of type date is not JSON serializable`，异常被 FSM 通用兜底吞成
  「跳过工具循环」。修法：工具结果序列化统一 `default=str`——工具结果
  只是给模型看的文本，协议边界上把非 JSON 原生类型转字符串。
- **模型「自信跳过」工具**（产品缺陷）：模型常不调 search_knowledge 直接
  DONE，consult 回答就没有知识库依据（引用 0），绕过「只能基于知识库作答」
  的安全约束。修法：**代码层兜底**——只要本轮没查过知识库，强制补一次
  检索。宁多一次检索，不赌模型守约。

新增自检：`check_tool_loop.py`（fake LLM 两轮 + 真实分发器，6 项）；
pytest 单元 +13 项（history_block / 参数解析 / 证据块 / 工具 schema 校验）。
回归：pytest 48/48、smoke 82/82。

9. **Windows Git Bash 里 `curl` 传中文参数用的是 GBK 编码**（2026-09-26，D31 同轮）。

   - 测带中文参数的接口，用 Python httpx/requests（显式 UTF-8），不要用 shell 里的 curl；
   - 「同一份代码，进程内与 HTTP 行为不一致」时，第一反应应该是**检查请求参数
     在入口处长什么样**，而不是怀疑代码或进程状态 —— 参数损坏不报错，
     只会表现为「查不到」。

### 关于「桌面不停弹命令行运行框」——已定论，见 D22

**（本节原来是「我没能完全定论，如实说明」。现在有结论了，把过程完整留下。）**

**第一轮的错误结论**：我写了两个探针，两个都被证伪，于是我在文档里写
「`CREATE_NO_WINDOW` 是防御性的，不是弹窗的解药；把它说成修好了弹窗是不诚实的」。
**这句话本身是诚实的，但结论是错的** —— 我失败的是**测量方法**，不是「查不出来」。

两个探针错在哪：

- **数 `conhost.exe` 数量** —— 指标被调用者自己污染（Bash 工具每次执行都起一个控制台），
  反证模式 +1、修复模式 +4，方向都不可信。**这个指标从一开始就不该用**。
- **子进程自报 `GetConsoleWindow()`** —— 沙箱用的是 headless 控制台，
  这个值恒为 0，无法区分「有控制台但隐藏」和「没有控制台」。

**真正的突破点**：换一个不需要推断的指标 ——
**直接枚举当前会话所有可见的「控制台类」顶层窗口**（`EnumWindows` +
`IsWindowVisible` + `GetClassNameW`）。这个指标不依赖任何假设，
窗口在不在屏幕上就是答案。而且**判据不能限定宿主进程**：
Windows 11 默认终端是 Windows Terminal，PG 自建的控制台挂在
`CASCADIA_HOSTING_WINDOW_CLASS` 上，只查 `conhost.exe` 会全部漏掉
（我 v2 就是这么得出反向结论的）。

换成这个指标后，一次单变量对照就出结论：
`DETACHED_PROCESS` → 新增 **4** 个可见窗口；`CREATE_NO_WINDOW` → **0** 个。
完整分析见 **D22**。

**教训**：查不出来的时候，先怀疑自己的**测量方式**，而不是急着宣布「无法确证」。
「无法确证」是一个结论，它也需要证据。

**另外一条仍然成立的观察（不在本项目内）**：排查时发现系统里有
**4 个 `weixinpay` MCP 服务的 `cmd.exe` 实例**，各自带一个 `conhost.exe`，
父进程互不相同：

```
PID=19076 PPID=824     conhost 27444
PID=23724 PPID=6872    conhost 21768
PID=46568 PPID=41520   conhost 31188
PID=23008 PPID=37996   conhost 46120
```

`cmd.exe /d /s /c` 是**会创建控制台**的。这属于插件/宿主层面，不在本项目代码里，
我没有动它（**不动用户没让我动的东西**）。如果按 D22 修完仍有弹窗，
下一个该看的方向就是这里 —— 判断方法同上：枚举可见控制台窗口，看 owner 是不是它。

### ★ 「降级模式全绿」不等于「真实模型可用」

这是本轮最值得记住的一条。

项目一直有意支持「无 Key 降级」（没有 API Key 也能跑通全链路，用模板生成回答），
所以此前所有检查都是在**降级分支**上跑的，全绿。但**填好 API Key 这个动作，
本身就是一次「启用一批从没被跑过的代码路径」**。结果一填完就冒出三个问题：

| # | 问题 | 为什么降级模式下永远看不到 |
|---|---|---|
| D30 | 意图识别提示词缺少「求解释 ≠ 求诊断」 | 降级模式走启发式，而启发式里**恰好写对了**；LLM 一上来就把它覆盖掉 |
| — | `LLM_VISION_MODEL` 留空会回落到主模型，而主模型不是 VLM | 降级模式下没有视觉调用，`vision_enabled` 只检查 Key 非空，一直报 true |
| — | `LLM_BASE_URL` 填的是 DeepSeek 官方地址，而 key 属于硅基流动 | 降级模式下压根不发请求，401 无从暴露 |

★ 三条都是**同一个形状**：健康检查说「配好了」（`llm_enabled=true`），
而它**只检查 Key 是否非空**，不验证 base_url、不验证模型名、不验证模型能力。
所以：

> **凡是「配置开关一开就换一条代码路径」的地方，都必须有一条
> 「用真实配置真的跑一次」的验证** —— 不能只看那个布尔标志。

落到这个项目就是 `scripts/_probe_llm.py`（三条链路实测）和
`backend/scripts/check_intent_llm.py`（真实 LLM 下的意图分类，正反两个方向）。
这两个脚本的价值不在于它们跑了多少次，而在于它们**在「配置好了」之后
还敢再问一次「真的好了吗」**。

★ 顺带：这也是为什么「填完 Key 就该重启 + 重跑一遍全部检查」不是仪式感 ——
重启会让原本不被执行的代码开始执行，回归套件是唯一能告诉你
「新启用的那条路是坏的」的东西。本轮就是这样抓到 D30 的。

### 待决策

1. **`margin` 分量的动态范围偏窄**（实测常态落在 0.01~0.10，只有两条检索通道
   判断分歧时才跳到 0.4~0.6）。这不是 bug——两条通道都支持同一组候选时，
   系统本来就应该说「分不清」。但若发现闸门过严，**应该调
   `CONFIDENCE_THRESHOLD`，不要放大 `CONFIDENCE_W_MARGIN`**。
2. **无 LLM Key 时闸门 A 在纯文字场景不拦截**（有照片才是硬闸门）。
   当前设计决定，已在代码注释说明理由；接入真实模型后需重新评估。
3. **MinIO 现在是个「装饰」**（见 D25）。本机装的 Aistor 缺 license，
   所有 S3 操作被拒，对象存储实际走本地磁盘。业务不受影响，但三条路要选：
   - **接受现状**：`storage` 字段已会如实报 `local`，前端也会提示降级。
     适合「先把流程跑通」的当前阶段。← 倾向这个
   - **换一个 S3 兼容实现**：SeaweedFS / Garage 都是活跃的开源项目，
     只需改 `storage.py` 里的一个类（接口已经抽好了）。
   - **装 license**：商业授权，对本项目没必要。
   除非面试时要专门演示「对象存储」这一环，否则不值得现在花时间。
4. **接真实天气源时用新版还是旧版 API**（需要你确认）。
   和风天气现在有两套接口，**认证方式和路径都不一样**：

   | | 新版（推荐） | 旧版（存量项目） |
   |---|---|---|
   | 认证 | 请求头 `X-QW-Api-Key` | 查询参数 `key=` |
   | 域名 | 控制台分配的**专属 API Host** | 固定的 `devapi.qweather.com` |
   | 路径 | `/weather/v1/current/{lat}/{lon}` | `/v7/weather/now?location=lng,lat` |
   | 响应 | **全部 Gzip 压缩** | 明文 JSON |

   你 `.env` 里填的是一个**专属 Host 形状**的地址（`xxx.xy.qweatherapi.com`），
   说明控制台给的是新版 —— 只是那串是官方文档的示例值。
   所以倾向按**新版**实现。但这需要你从
   [控制台-设置](https://console.qweather.com/setting) 里取出自己的真实 Host，
   否则写完也没法验证（我不会交一段没跑通的东西）。
